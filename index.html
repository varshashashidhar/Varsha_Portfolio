Case study · Design systems

Closing the detach gap

Every time a designer detaches a component, the thread from canvas to production code breaks, and the reason why disappears with it. What if every detach made the design system stronger instead of weaker?

Problem

Detaches are visible to design system teams only as counts, after the fact. The why (a missing variant, an unsupported override) is lost, so drift compounds quietly across files and into code.

Bet

Capture intent at the moment of detaching with near-zero friction, turn it into prioritized, AI-drafted fixes for system owners, and keep engineers on-system in Dev Mode even when the design drifted.

How we'd know

Fewer repeat detaches on components that received a gap-driven update, faster time from pattern to published variant, and more Dev Mode inspections that resolve to real code components.

01

Context

Figma libraries let a design system team publish components, variables, and styles once and keep every file across an organization in sync. Dev Mode and Code Connect carry that system across the handoff: an engineer inspecting a button can see the real production component, not just pixel specs. At its best, the design system is a single thread from a designer's canvas to shipped code.

02

Problem & users

That thread breaks whenever someone detaches an instance to make a one-off change. The layer stops receiving library updates, and its link to the coded component is gone. Detaching isn't the enemy: it's often the fastest way for a designer to get unblocked. The problem is that the signal inside each detach is thrown away.

Product designer

"I need this button with an icon today. The component doesn't support it, so I detach."

Pain: blocked by gaps; any added friction feels like punishment.

Design system owner

"I can see detaches going up, but not why. I find out what's missing in a review three weeks later."

Pain: reactive roadmap, no prioritized evidence.

Front-end engineer

"This layer isn't linked to anything, so I rebuild it by hand from the specs."

Pain: off-system code, inconsistency, rework.

03

Why now

  • AI raises the stakes on coverage. Workflows that generate designs or code from your components are only as good as the system they draw from. Gaps that used to cost one designer an afternoon now get reproduced at machine speed.
  • Design-to-code is becoming the product. As Dev Mode and Code Connect make the design-to-production link real, every broken link is more visible, and more expensive.
  • Enterprise scale compounds drift. For a customer with hundreds of teams, a missing variant isn't one detach; it's the same detach, hundreds of times, in hundreds of files.

    05

    Metrics

    Hypotheses I'd validate with real baselines before setting targets.

    North star

    Repeat-detach rate on updated components

    Share of detaches, per active instance, on components that shipped a gap-driven update. If the loop works, this falls.

    Input

    Reason capture rate

    % of detaches with a reason. Tells us whether the prompt is light enough to use.

    Input

    Gap → published time

    Median days from a recurring pattern to a published variant.

    Outcome

    On-system inspections

    % of Dev Mode inspections that resolve to a Code Connect component.

    Guardrail

    Designer speed

    Time in the detach flow and prompt dismissal rate. The feature fails if designers feel slowed down.

    06

    Rollout

    1. Phase 1 · Listen

      Instrument without asking. Log a structured summary of what changed on detach (no prompt). Validate that diffs cluster into a small set of real gaps.

    2. Phase 2 · Ask lightly

      Sampled prompt, design-partner beta. Enable the reason prompt for a few enterprise design system teams. Ship the Gaps view to owners. Watch the guardrails closely.

    3. Phase 3 · Close the loop

      AI drafts and Dev Mode routing. Add AI-drafted variants for top gaps and nearest-component routing for engineers. Offer one-click re-linking of detached layers after a fix ships.

    07

    Risks & open questions

    Tradeoffs I'd watch

    • Friction on a power-user action. Keep the prompt optional, inline, and sampled; never block the detach.
    • Noisy AI inference. Explicit reasons lead; diff-based inference assists and is shown with confidence.
    • Permissions. Aggregating across an org must respect file access and team boundaries.
    • Owner overload. Rank by volume and impact so the view stays a roadmap, not a queue.

    Questions I'd bring to the team

    • What share of detaches are truly "missing variant" vs. intentional one-offs that should stay detached?
    • Should solo designers and small teams see this at all, or is it an enterprise-tier workflow?
    • How should this connect to existing library analytics rather than live as a separate surface?
    • Could the same signal power design-system suggestions in AI generation flows?
